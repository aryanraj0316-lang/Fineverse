# Render image delivery and scroll performance

The previous image pipeline encoded AVIF on demand. The replacement builds WebP variants before Next.js builds and serves them as static files. scripts/build-static-images.mjs creates content-hashed 320/640/960/1440/1920 variants without upscaling, preserves transparency and writes data/static-image-manifest.json. Already small WebP catalog images are served directly. No external image service or API key is needed. The output public/image-cache/ is ignored by Git and regenerated by npm run build and npm run dev. Commit the script, loader, config and manifest, plus source assets; do not skip prebuild during deployment.

Hash-named images cache for one year; other static images and sequence frames cache for one day. Product HTML is not covered by the asset-cache rule. Hero picture sources use the same static mapping on the server.

Scroll sequences retain scrolling, labels and reverse scrubbing. Decoding caps image width at 640 on desktop / 480 on smaller screens, uses two workers, prioritizes the current scroll target, releases offscreen scenes and avoids resetting canvas dimensions unnecessarily.

Verification: 557 responsive variants for 139 sources, every manifest file exists; hero watch 640px file 43 KB versus original PNG 861 KB. Production browser check: visible images decoded, zero /_next/image requests, no broken image responses or page errors, cache headers verified. Forward/reverse frame and label checks cover five viewports.

Render build command: npm ci --include=dev && npm run build. Start: npm run start -- --hostname 0.0.0.0 --port $PORT. Deploy the new commit before checking hosted behavior. A Free service still has Render cold starts after idle; these code changes do not remove platform sleep. Live deployment URL and response/log inspection are needed to confirm whether missing committed assets or platform errors also affect the hosted site.
